13: Comment 2:  The proposed adaptive coefficient-learning mechanism is presented as a key AI contribution, but it was not actually trained or validated using real operational outcomes, so its practical effectiveness remains unverified.
14: Response:  This was correct and the manuscript now separates two different things that the earlier version ran together. What the system implements is a bounded heuristic adaptation: the five scoring weights are regenerated each dispatch cycle from measurable operating context and from per-corridor correction factors refitted on completed-trip residuals, with every learned correction clipped at ±0.15. That mechanism is implemented and it is now evaluated, as a seed-matched paired ablation against the static mode, and separately in a multi-day closed-loop experiment. What the system does not do is train a softmax-parameterised weight vector by gradient descent on a cross-entropy objective. Those relations are retained as mathematics but are labelled throughout as a proposed extension that has not been run. We also report that the learning component was invoked zero times during the 36 scalability runs, because a single dispatch pass produces no completed trip and therefore no residual.

23: Comment 4:  Per-service-type or per-request performance results are not provided by the study, so it is unclear whether the reported gains are consistent across passenger, food, and parcel services or are mainly driven by one category.
24: Response:  We attempted this for the camera-ready and report the outcome exactly. Service type is recorded at the request level: SimulationRequest.request_type carries ride, food or parcel, and Trip.request_ids_json links each trip back to its requests, so the join exists in the schema. What does not exist is any type-aware outcome aggregation: distance, delay, fuel, utilisation and CO2 are computed per trip, and the only per-type quantity written to the result files is the input request mix. Two obstacles then prevented us from producing the breakdown. First, the per-trip database from the 36 runs is not recoverable — the harness recreates its database on every run and that database no longer exists, and no result file retains trip-level records. Re-running the experiments was not possible in the environment available for this revision, because OR-Tools is a hard dependency of the routing stage and could not be executed there. Second, and more fundamental than tooling: at the two larger workloads 83.3% of trips are shared, and a shared trip routinely carries requests of different types. Splitting one shared trip's distance or fuel between a food order and a passenger ride requires a cost-allocation convention that the system does not define, so even a re-run would not yield a per-type efficiency figure without introducing an assumption we would have to invent. We therefore report the request mix, state plainly that outcome metrics are not split by it, and record the gap as a limitation rather than apportioning the aggregates.

54: Comment 4:  Authors should clarify the privacy and data-handling procedure for location information and aggregated operational data.

59: Comment 5:  It is suggested to explain the practical implications of relying on Google Maps API data for route and travel-time estimation.
60: Response:  The manuscript now separates three things that were previously blurred. First, the implementation calls the Google Maps Distance Matrix API when a key is configured and falls back to a haversine matrix otherwise; the fallback is to a local computation, not to a second commercial provider, and no alternative provider is implemented. Second, the reported experiments were run deliberately with the key unset so that the haversine path is used and the runs reproduce without network access; all 1,869 trips were computed this way and no external call was issued. Third, the practical implications are stated: per-call cost and quota limits that grow quadratically with pool size given pairwise scoring, added network latency in every dispatch cycle, and degraded route quality under slow or stale responses, with the haversine fallback keeping the pipeline running at the cost of road-network and traffic awareness.
61: Change made:  Section IV-B states the API configuration used for the experiments and why. A limitation covers cost, quota, latency, degradation and the nature of the fallback, and states that no alternative commercial provider exists in the implementation.

64: Corrections not arising from a reviewer comment
65: Two further corrections were made after re-reading the implementation, and we note them here rather than leaving them to be discovered. First, the architecture figure and Section III-C previously described routing as preceding driver assignment. The implementation does the reverse: the driver and vehicle are selected first, and the route is then optimised for that vehicle, because the routing objective prices fuel through the vehicle's own efficiency. Figure 1 was redrawn from the dispatch code and Section III-C now presents the two stages in the implemented order, with equations (8) and (9) exchanged accordingly. Second, the driver selector uses five weighted factors, not three; equation (9) previously showed only proximity, vehicle type and workload, and now includes rotation fairness and historical completion rate with their configured coefficients.

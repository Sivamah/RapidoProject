No code was executed; every row below is backed by a file:line citation in the Evidence Notes for anything not marked plain "Working".

## Evidence Notes

### 6. Dispatch — Partial
- `frontend/src/hooks/useOperationalNetwork.js` and every `frontend/src/pages/*.jsx`/`components/**/*.jsx` file were grepped for the literal strings `dmfe/run`, `/run'`, and `assign/driver` — the only DMFE-prefixed calls the frontend ever makes are `GET /dmfe/trips`, `GET/POST/DELETE /dmfe/batches|statistics|history|analyze|demo/seed|demo/clear` (all in `dmfe_v2.py`). None of `dmfe_engine.py`'s pipeline endpoints (`compatibility-score`, `context`, `batch/create`, `optimize/route`, `assign/driver`, `/run`, `trips/{id}/complete`, `assignments`) are called from any React file.
- `dmfe_v2.py`'s own module docstring (lines 1-16) is explicit: `"No OR-Tools, no vehicle assignment, no routing."` — confirming that `POST /dmfe/analyze` (the button the UI actually wires up) performs Compatibility + Batching only, and cannot itself dispatch, assign drivers/vehicles, or complete trips.
- `backend/app/services/simulation_service.py:651-654` shows the *actual* dispatch trigger is inside the background simulator: `if pending_count >= 6 and (tick_count % 3 == 0): ... result = pipeline_runner.run(db, limit=200)`. This only runs once `POST /simulation/start` has been called and only fires conditionally on a tick counter and queue depth — there is no way for an operator to force an immediate dispatch cycle from the UI.

### 7. Driver assignment — Partial
- Repo-wide grep of `frontend/src` for `assign/driver` and `assign_driver` returns zero matches; `POST /api/dmfe/assign/driver` (`dmfe_engine.py:242-299`) is unreachable from the UI.
- The only frontend-visible surface for this feature is read-only: `pages/DriverDashboard.jsx:55` → `api.get('/drivers/assignments/history?limit=100')` → `drivers.py:215-218::get_assignment_history()`, which shows the *results* of assignments the background simulator already made, not a UI-initiated assignment.

### 8. Vehicle assignment — Partial
- Same gap as feature 7: the trip-time vehicle pick inside `dispatch_trip()` (`dmfe/driver_selection.py`) has no direct frontend trigger.
- `pages/DriverDashboard.jsx:124` (`api.patch('/vehicles/${id}', vehicleData)`) and `:93` (`api.patch('/drivers/${id}', driverData)`) do give the UI real, working control over *fleet-roster* vehicle↔driver linking (`drivers.py:73-101,177-189`), but that is a distinct concept (which vehicle a driver is permanently assigned in the roster) from "which vehicle got assigned to this dispatched trip," which remains simulator-only.

### 9. Trip completion — Partial
- Grep of `frontend/src` for `trips/.*complete` returns zero matches. `POST /api/dmfe/trips/{trip_id}/complete` (`dmfe_engine.py:364-381`) exists and is fully implemented (calls `driver_selection.py::complete_trip()`, which the docstring at `dmfe_engine.py:370-376` explains is load-bearing for releasing drivers/vehicles back to the pool) but no page or component calls it.
- The only completion path reachable from the UI is automatic, via `simulation_service.py:681-713`, which completes any `Trip` in `Planned`/`Active` status older than a randomized 60-120s window, on each simulator tick.

### 12. XAI → Map — Partial
- `frontend/src/pages/LiveSimulationMap.jsx:43` carries the comment `// ── XAI Focus (from "View on Map" on the XAI dashboard) ─────`, describing a UI element named "View on Map" that is supposed to deep-link into this page via `?xai=<id>`.
- A repo-wide grep for the exact phrase `View on Map` across all `.jsx`/`.js` files under `frontend/src` returns exactly one hit — the comment itself (`LiveSimulationMap.jsx:43`) — no button, link, or `<a>`/`<Link>` element with that label exists.
- A repo-wide grep for `navigate(` and `<Link` (`frontend/src` command: `grep -rn "navigate(\|<Link\|useNavigate" --include="*.jsx" .`) shows only two `navigate()` calls in the whole app (`pages/Dashboard.jsx:277` → `navigate('/live-map')`, `pages/Login.jsx:24` → `navigate('/dashboard')`), and neither ever appends a `?xai=` query string. `AdminLayout.jsx`'s sidebar link to `/live-map` is also bare, with no query param.
- Consequently the `xaiParam` handling in `LiveSimulationMap.jsx:44-70` (which calls `GET /api/xai/explanations/${xaiParam}` and correctly renders via `normalizeXaiHighlight()`) is functionally correct and backend-verified (`backend/tests/test_xai_map_link.py`), but is currently unreachable through any control in the shipped UI — it only activates if a URL containing `?xai=<id>` is typed or bookmarked manually.
- The feature nonetheless *works* through a different, fully-wired path: `pages/ExplanationDashboard.jsx:59-67` (`handleCardClick`) passes the selected explanation object directly as a prop to `components/xai/XaiMapPanel.jsx`, which renders the same `normalizeXaiHighlight()` output in an inline map panel without needing the `/live-map` route or a second network call at all.

### 3. A-DMFE / 4. Compatibility / 5. Batching — Working, with an unreachable secondary endpoint noted
- `POST /api/dmfe/batch/create` (`dmfe_engine.py:164-200`) and `POST /api/dmfe/compatibility-score` (`dmfe_engine.py:100-117`) and `GET /api/dmfe/context` (`dmfe_engine.py:120-161`) all exist, are fully implemented, and are exercised only by `backend/tests/` (via direct Python calls to engine modules, not via HTTP), never by the frontend — the UI's "Run Analysis" button uses the separate, older `dmfe_v2.py::/analyze` endpoint exclusively, which produces the same persisted `DMFEBatch` rows through a different code path (`decision_engine.py`, not `dmfe_engine.py`'s granular per-stage endpoints).

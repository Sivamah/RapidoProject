# ICCES-260 Reviewer-Experiment Package — DMFE / A-DMFE

This package contains the experiment scripts written for the ICCES-260
reviewer-experiment request.  They evaluate the **current** DMFE / A-DMFE
implementation in the isolated, disposable evaluation harness.

## Scope and safety

- All scripts run **inside this `backend/evaluation/` directory**.
- Every script points `DATABASE_URL` at the isolated **`experiments/eval.db`**
  (via `framework.py`) and calls `ExperimentDB().reset_schema()` to create a
  fresh schema for its own run.  **No production / dev database
  (`dmfe_dev.db`) is ever read or written.**
- No core application module is modified by any script.  Scripts call the real
  dispatch pipeline through `WorkloadRunner` / `PipelineRunner`, exactly as the
  other harnesses in this folder do.
- Scripts fail loudly if they cannot reproduce their required workload — they
  never fabricate rows or results.

## Experiment scripts (reviewer mapping)

| Script | Reviewer mapping | What it measures |
|--------|------------------|------------------|
| `per_service_breakdown.py` | R1.4 | Per-service (ride / food / parcel) dispatch + batching breakdown over workloads, with full reconciliation. |
| `exact_matching_baseline.py` | R1.3 | Exact (optimal) vs greedy pair-matching on the **pairing sub-problem**, stdlib-only. No networkx. |
| `robustness_r11.py` | R1.1 | 8-profile robustness sweep: 2 demand levels (LOW/HIGH) × 4 temporal shapes (morning peak / midday flat / evening peak / night sparse). Temporal variation applied to the real `request_timestamp` field. |
| `time_window_sensitivity_r21.py` | R2.1 | Time-window (max-delay) sensitivity: sweeps the actual `SystemConfig.max_allowed_delay_min` knob (10/15/20/25/30). |
| `acceptance_r15.py` | R1.5 | Acceptance **simulation** under an explicitly assumed model (priority-weighted dispatch + fulfillment). Not a human study. |

## Outputs

Each script writes a JSON report under `results/`:

```
results/r11_robustness.json      results/r14_per_service.json
results/r13_exact_matching.json  results/r15_acceptance.json
results/r21_time_window.json
```

## Running

From `backend/` (uses the backend virtualenv Python):

```
.venv\Scripts\python.exe evaluation\per_service_breakdown.py
.venv\Scripts\python.exe evaluation\exact_matching_baseline.py
.venv\Scripts\python.exe evaluation\robustness_r11.py
.venv\Scripts\python.exe evaluation\time_window_sensitivity_r21.py
.venv\Scripts\python.exe evaluation\acceptance_r15.py
```

Each run is seeded deterministically and is reproducible run-to-run (see
`DEBUG_REPORT.md` for the reproducibility verification).

## Dependencies

`framework.py`, SQLAlchemy, and the application code already in the repo.
`exact_matching_baseline.py` uses only the Python standard library for the
exact matching algorithm (networkx is intentionally NOT used — it is not
installed and not in `requirements.txt`).

## Honesty notes

- R1.5 is strictly a **simulation** of acceptance under a stated model — it is
  not a human study and makes no user-preference claims.
- R1.1 temporal variation uses the `request_timestamp` field that the current
  engine actually reads; it does **not** inject a fake per-request time-window
  column that the engine does not support.
- All metrics are over synthetic requests generated by the existing
  `generate_simulation_requests` harness.
